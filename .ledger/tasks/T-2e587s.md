## Spec

Embed TOOL_VERSION, SCHEMA_VERSION, PROTOCOL_VERSION constants in ledger.py and add 'ledger doctor --json' reporting {tool_version, schema_version, protocol_version, config_schema_version, repo_compatible, canonical_source: github.com/Sleepy9099/ledger}. Config 'version' becomes the storage-schema version explicitly. Offline only - no network calls. Purpose: repos bootstrapped at different points in the tool's evolution can tell whether their vendored copy is stale and whether their task corpus matches the schema the tool expects.


### Enrichment from the external multi-agent review triage (2026-09-01)

- `config.version` is written only on first init (the existing-config branch never rewrites config.json) and is never read anywhere, so it can lag both the tool and the corpus. Derive `corpus_schema_version` from task headers, not from config: any status value outside STATUSES or any key outside HEADER_ORDER ⇒ "corpus newer than tool", `repo_compatible: false`, `ok: false`, exit 1, one `errors[]` entry with code `schema-mismatch` (a doctor code — keep VALIDATION_CODES and its lockstep test unchanged) and fix_hint "run `python <newer>/ledger.py init` from the repo root" (init copies itself into .ledger/ and refreshes PROTOCOL.md/CLAUDE.md). Report `config_schema_version` (declared) separately from the inferred value. `config.version` must NEVER be written by task-mutating commands (config.json must not become a merge hot spot — DESIGN core bet 2); whether `init` may raise it on an existing repo is an open question of this task.
- SCHEMA_VERSION bump rule: any change an older copy reports as an `enums` / `parse` / `state-coherence` ERROR (new status value, new required key, new claim pairing) bumps it; a purely additive header key does not (older copies emit only the `unknown-key` warning). Today 1 = the DESIGN §2 header. The `ready`-status decision task filed 2026-09-01 would add 2 if approved — it must itself add the row.
- Ship the unavoidable-path lever first (core bet 1): change the `enums` fix_hints from "one of: ..." to "one of: ...; if this file was written by a newer ledger.py, update the vendored copy instead of editing the value" — an old copy will never have `doctor`, so the mismatch signal must ride on `validate`.
- Observed old-copy behaviour on a newer corpus (scratch run): `next` hides an unknown-status task with an empty `why`; `claim` rewrites it to in_progress; `list --status` cannot filter on it (argparse exit 3); mutating verbs write straight through it — the fix_hint should add "do not run mutating commands from this copy against this corpus".
- Pre-doctor copies return argparse exit 3 (no envelope) for `doctor`; document "treat exit 3 as tool predates doctor". PROTOCOL_VERSION is what every task that edits PROTOCOL_TEXT should bump — of the tasks filed 2026-09-01: T-w0emnj (which owns the sequencing and size budget), T-ntt2zz, T-z7iebd, T-yfvuya, T-eb6bas, T-z1dkju, T-5z04ex and the T-zl7jh5 enrichment.
- Offline means no git history/repo calls (never touch ctx.repo, walk_commits, git_head); the only git call allowed is the actor lookup in make_ctx, which --session/LEDGER_SESSION bypasses.
- Tests: subprocess fixture with a hand-written unknown status → `schema-mismatch`, exit 1; plain corpus → compatible; re-init on an existing repo leaves config.json bytes unchanged (extends the existing init test); in-process monkeypatch via the `ledger_mod` fixture for the reverse case.
